# Dict Keeper 设计说明

## 背景

- `import-pipeline` 是早期的数据导入工具，提供了较强的通用配置能力，但也把大量底层请求细节暴露给了用户。
- `dict-keeper` 的目标不是替代一个通用请求工作台，而是围绕“数据字典”和“字典项”提供稳定、低操作成本的业务工具。
- 在 `dict-keeper` 成熟后，`import-pipeline` 的产品入口将关闭，仅保留为内部调试或诊断能力。

## 产品目标

### 核心目标

- 聚焦数据字典与字典项的增删改查。
- 尽可能减少用户操作，降低接入和日常使用成本。
- 隐藏底层请求细节，不要求用户手工填写接口地址、请求头、模板参数等低层配置。
- 允许通过一次录制或少量确认，生成可长期复用的数据源预设。

### 设计原则

- 业务逻辑固定，系统差异适配。
- 规则引擎优先，AI 或智能推断仅做辅助排序和低风险建议。
- 默认路径优先满足高频场景，不为极端场景牺牲整体复杂度。
- 所有有副作用的动作都必须可追踪、可回滚、可清理。

## 非目标

- 不构建通用工作流编排平台。
- 不提供任意脚本执行入口给终端用户。
- 不要求用户理解底层网络请求结构。
- 不依赖第三方在线 AI 平台完成核心逻辑。
- 不追求对完全陌生系统的零确认自动接入。

## 业务范围

Dict Keeper 仅关注两个领域对象：

### 数据字典

- 查询字典列表
- 新增字典
- 编辑字典
- 删除字典

### 字典项

- 查询指定字典下的字典项列表
- 新增字典项
- 编辑字典项
- 删除字典项
- 批量导入字典项

## 领域模型

### Dictionary

- `id`: 字典唯一标识
- `code`: 字典编码
- `name`: 字典名称
- `description`: 字典描述
- `status`: 字典状态
- `createdAt`: 创建时间
- `updatedAt`: 更新时间

### DictionaryItem

- `id`: 字典项唯一标识
- `dictId`: 所属字典 ID
- `label`: 展示名称
- `value`: 实际值
- `remark`: 备注
- `sort`: 排序值
- `parentId`: 父级字典项 ID
- `status`: 状态
- `createdAt`: 创建时间
- `updatedAt`: 更新时间

说明：

- 实际接入不同系统时，字段名可能不同，但 Dict Keeper 内部应统一为上述标准模型。
- 任何外部请求、响应、页面结构都必须先被适配为标准模型，才能进入业务层。

## 产品形态

### 日常使用路径

用户默认只感知以下几个动作：

1. 选择或搜索一个数据字典。
2. 查看字典详情和字典项。
3. 新增、编辑、删除字典或字典项。
4. 将一批数据导入到当前字典。

### 首次接入路径

首次接入某个系统时，只允许两种方式：

1. 选择一个现成的数据源预设。
2. 录制一次真实操作，生成候选预设后由用户确认。

默认不暴露底层请求配置面板。

## 核心架构

整体采用四层结构：

### 1. UI 层

职责：

- 展示字典和字典项列表
- 提供新增、编辑、删除和导入入口
- 显示学习结果、错误、日志和必要确认

对应当前工程中的主要承载位置：

- `src/dict-keeper/viewer.vue`
- `src/dict-keeper/setting.vue`
- `src/dict-keeper/preview.vue`

### 2. 领域层

职责：

- 只面向 `Dictionary` 和 `DictionaryItem` 两类标准对象编程
- 提供稳定的 CRUD 用例
- 不关心目标系统的接口细节和页面细节

这一层是 Dict Keeper 的业务核心。

### 3. 数据源适配层

职责：

- 将不同系统的接口、响应、页面行为转换为统一领域接口
- 隐藏 `dictId` 获取、探针回查、清理补偿等系统差异
- 对外只暴露固定的字典与字典项能力

这是替代“通用工作流编排”的关键层。

### 4. 基础设施层

职责：

- 请求观测
- 录制与回放
- 本地存储
- 调试工作台
- 日志与错误跟踪

`import-pipeline` 在产品层退场后，可以保留在这一层，作为内部调试能力存在。

## 为什么不用通用工作流编排

如果把“创建字典、解析 dictId、创建字典项、删除探针、回滚补偿”全部暴露成可配置工作流，复杂度会迅速失控：

- 用户需要理解执行顺序和失败分支。
- 系统会重新长成一个新的 `import-pipeline`。
- 任何自定义脚本或自由编排都会显著提高测试和维护成本。

因此，Dict Keeper 不做通用工作流平台，而是采用以下策略：

- 产品流程固定。
- 目标系统差异封装在“适配器”内部。
- 用户只在低置信度场景下做一次确认。

## 数据源适配器

### 适配器职责

每个数据源适配器需要屏蔽目标系统差异，并对外提供统一能力：

- 查询字典列表
- 创建字典
- 更新字典
- 删除字典
- 查询字典项列表
- 创建字典项
- 更新字典项
- 删除字典项

### 适配器内部可以处理的复杂逻辑

- 从创建响应中提取 `dictId`
- 通过列表或搜索接口回查 `dictId`
- 通过详情页路由或详情请求兜底获取 `dictId`
- 插入探针数据辅助定位目标对象
- 删除探针数据并执行失败补偿
- 对目标系统字段名和返回结构做归一化

### 适配器设计原则

- 对外接口固定
- 对内策略可替换
- 不向上层泄漏请求模板和临时推断细节

## 录制功能的定位

录制不是为了生成“通用工作流”，而是为了生成“候选适配器预设”。

### 录制阶段需要采集的信息

- 用户点击、输入、选择等关键操作
- 路由变化
- 请求与响应
- 请求发起前后的页面状态变化
- 目标对象的关键字段样本

### 录制功能的产物

录制结束后，系统输出的是一份候选预设，包含：

- 哪些请求更像字典 CRUD
- 哪些请求更像字典项 CRUD
- `id` 更可能出现在什么位置
- 哪些字段更像 `name`、`code`、`label`、`value`
- 是否需要探针或回查策略

录制只做建议，不直接决定最终控制流。

## AI 的使用边界

项目不依赖第三方在线 AI 平台完成主逻辑。

如果后续引入本地模型，只允许用于以下辅助场景：

- 字段语义匹配
- 请求角色分类
- `id` 路径候选排序
- 低置信度候选打分

以下能力必须由规则和代码实现：

- 主流程执行顺序
- 失败重试
- 探针数据创建
- 回查逻辑
- 清理和回滚
- 权限和安全判断

结论：AI 只能做辅助判断，不能接管流程编排。

## 用户操作最小化策略

为了尽可能减少用户操作，Dict Keeper 应优先遵循以下策略：

### 高频路径自动化

- 记住最近使用的数据源预设
- 记住最近进入的字典
- 批量导入时自动绑定当前字典
- 成功操作后自动刷新列表
- 常规表单自动填入合理默认值

### 低置信度才打断用户

- 当系统无法确定 `dictId` 来源时，再要求用户确认
- 当候选请求存在多个高相似项时，再要求用户确认
- 删除类操作保留明确确认步骤

### 高级配置收口

设置页只暴露少量必要配置：

- 数据源选择
- 候选预设确认
- 是否允许探针策略
- 调试日志开关
- 危险操作安全开关

不暴露以下内容给普通用户：

- 原始 endpoint
- 请求头 JSON
- 动态模板
- 自定义脚本
- 任意流程分支

## 分阶段落地建议

### Phase 1：固定业务闭环

目标：先跑通稳定业务，而不是追求全自动。

- 定义统一的 `Dictionary` 和 `DictionaryItem` 模型
- 基于适配器接口实现字典与字典项 CRUD
- 完成“已有字典下导入字典项”能力
- 将 `import-pipeline` 收缩为内部调试工具

### Phase 2：录制生成候选预设

目标：降低首次接入成本。

- 增加录制与请求观测能力
- 根据录制结果生成候选适配器预设
- 允许用户确认后保存为本地预设

### Phase 3：增强自动探测

目标：继续减少用户操作，但不引入通用编排平台。

- 增加 `dictId` 解析兜底策略
- 增加探针数据自动清理能力
- 增加低置信度排序与确认流程

### Phase 4：本地智能辅助

目标：只用本地能力改善匹配效果。

- 引入本地模型做字段语义匹配和请求分类
- 保持规则引擎为主，模型为辅

## 当前结论

Dict Keeper 的正确方向不是把 `import-pipeline` 继续包装成更复杂的配置产品，而是：

- 收束业务范围
- 固定主流程
- 引入数据源适配器
- 用录制生成候选预设
- 用规则隐藏复杂度

最终，用户面对的是“数据字典管理器”，而不是“请求工作流编辑器”。
